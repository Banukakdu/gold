# Spec: Recurring expense templates (create an expense from a saved template, e.g. rent)

## 1. Goal and scope
Backlog **AG-066** (E7 Income & Expense Recording, Could, R3, 3 points): "As a Cashier, I want recurring expense templates (e.g. rent) so that regular payments are faster to enter." AC: template stores account, category, amount, payee; "Create from template" pre-fills the form. Project document: E7 "Record entries with category, sub-category, payee/payer, attachments; edit/void; recurring templates"; supporting table `recurring_templates` ("templates for recurring entries").

**A template is a saved pre-fill for the Record expense form. It posts nothing.** Creating, editing, archiving or restoring a template never writes `transactions`, `ledger_entries` or `accounts.current_balance`. Using a template opens the normal expense form, already filled in. The user checks it and presses Save. That runs the existing `POST /v1/expenses` and `LedgerService::incomeOrExpense` with every existing check: account active and of the branch; category active, of type expense, global or of the branch, parent active; amount > 0; date <= today; period lock and fiscal year open; `assertFunds` in block mode; the AG-064 approval hold (R2 and R2b).

**Decision: no automatic or scheduled creation (Q4).** The backlog asks only for "Create from template". An automatic posting is **not acceptable** in this system, and this spec does not build one, not even as an option:
1. An expense credits a money account, so it records that cash or bank money **has left**. A scheduler cannot know that the rent was actually paid, on which day, from which account or for how much. A posting made without that knowledge is a false entry. The fix would be a void, which adds noise to the audit trail.
2. There would be no human `created_by`. AG-064 needs a requester: R4 says the requester never approves, R4a decides who may approve, and R2b sums the same-day total per user. A system user would either bypass the hold (as Super Admin expenses do) or create requests that nobody owns.
3. A nightly job would hit locked periods, closed years, "Insufficient balance" in block mode and inactive accounts with nobody there to decide. It would fail silently or post into the wrong period.
4. One template edit would repeat a wrong amount or payee every month without anyone looking at it.
5. Bank reconciliation (AG-033) would get book lines that exist only because a schedule ran, not because of a real bank movement.
If the business later wants reminders, the safe form is a **reminder only** (for example a "Not used yet this period" list or an in-app notification), never a posting. That would be a new backlog item. The S1 "This period" column (R9) already shows which templates have not been used yet this period.

What exists (`feature/bank-reconciliation`, 2026-11-20): `TransactionController::storeExpense` with `validated()` (`account_id`, `category_id`, `txn_date`, `amount` decimal 0-2, `payee_payer` max 255, `payment_method` in `cash,bank_transfer,cheque,card,online`, `reference` max 255, `description` max 2000); `EntryFormComponent` (`/transactions/new/:kind`) already reads `?account_id=` (AG-033), keeps the account and date after a save, and has the AG-064 hint (`needsApproval()` from the `amount` signal) and the AG-062 attachment picker; `Category::isEffectivelyActive()`; `Account::MONEY_TYPES` (`cash, bank, wallet`) and `status` (`active`, `inactive`, `closed`); the `BranchScoped` trait; `AuditLogController::GROUPS` and `LABELS`; "Record expense" is hidden in All branches mode (shell).

**Out of scope:** income templates (the story is about expenses; the table has a `type` column so income can follow without a schema change, but only `expense` is accepted); any scheduled, automatic or bulk creation (above); reminders or notifications about due templates (AG-094 is not changed); global or company-wide templates shared by several branches (Q9); stored attachments on a template (each bill brings its own receipt, Q6); placeholders in text such as "{month}"; splitting one template over several categories; a stored reference or bill number (it changes every time, Q6); hard delete of a template; an Excel export of templates.

## 2. Personas and permissions
**No new permission key.** The catalogue in `PermissionSeeder::PERMISSIONS` stays as it is. A new key would also be given to every `*` (Branch Admin) role automatically, and the existing keys already describe the rights:

| Action | Key (in the active branch) | Templates that have it |
|---|---|---|
| See the templates list (S1), the "From template" picker (S2), `GET` endpoints | `expense.create` **or** `expense.edit` | Branch Admin, Accountant, Cashier |
| Use a template (pre-fill and save an expense) | `expense.create` (the save is the normal `POST /expenses`) | Branch Admin, Accountant, Cashier |
| Create, edit, archive, restore a template | `expense.edit` | Branch Admin, Accountant |
| Everything, any branch | Super Admin (`canDo` is always true) | — |

Viewer has none of these keys and sees no Templates menu. A custom role with only `expense.create` may use templates but cannot change them.

**Why the Cashier uses templates but does not maintain them (Q1).** A template is standing payment data: who is paid (payee), how much, and from which account. If the person who pays could also change that data, a payee or amount change would go straight into the next payment with no second person involved. Maintenance therefore needs `expense.edit`, which belongs to the reviewers (Accountant, Branch Admin). Every change is audited with its old and new values (R11). Nobody may grant a key they do not hold; this is enforced by the existing Roles screen, unchanged.

## 3. User flows
- **F1 Accountant sets up rent (KDY Accountant, branch KDY).** Expense templates > "New template" > Name "Rent - Kandy office", Paid from KDY Bank, Category Rent > Office rent, Amount 150,000.00, Paid to "S. Fernando (landlord)", Payment method Bank transfer, Description "Monthly office rent", Repeats Monthly > Save > toast "Template saved." The template appears in the list with This period: "Not used yet (November 2026)".
- **F2 Cashier records this month's rent (KDY Cashier, branch KDY).** Record expense > "From template" picker at the top > "Rent - Kandy office". The form fills in: Date stays at today (2026-11-20), Paid from KDY Bank, Rent > Office rent, 150,000.00, Paid to, Bank transfer, Description. Reference stays empty. Info line: "Filled from template Rent - Kandy office. Check the date, amount and reference against the bill before saving." The Cashier types the reference, attaches the receipt and presses Save. The usual result appears ("Saved as KDY-EXP-2026-000510." or, above the KDY limit, "... sent for approval"). Alternative path: Expense templates > row "Use" opens `/transactions/new/expense?template=<id>` with the same pre-fill.
- **F3 Second use in the same month (duplicate).** On 2026-11-25 someone picks the template again. The form shows (warning) "Already used for November 2026: KDY-EXP-2026-000510 (posted, 2026-11-20)." Save returns 409 and the form shows the message with a "Save anyway" button. Pressing it resends with `confirm_duplicate: true`, the expense is saved, and the audit row records the confirmation (R6).
- **F4 Variable amount (electricity).** The template has no amount. Pre-fill leaves Amount empty and focuses it; everything else is filled in.
- **F5 Account closed later.** KDY Bank is set inactive. The S1 row shows the danger tag "Account inactive". Picking the template fills in everything except Paid from and shows "The template's account KDY Bank is inactive. Choose another account." The user may still save with another active account. An Accountant edits the template to fix it, or archives it.
- **F6 Archive and restore (Accountant).** S1 row menu "Archive" > optional reason > "Template archived." The template disappears from the list and the picker and shows under "Show archived". "Restore" brings it back unless an active template already has the same name.
- **F7 Super Admin, All branches.** Expense templates lists every branch's templates with a Branch column, read-only. "Use" says "Switch to KDY and use". It switches the active branch to the template's branch (as the AG-094 open flow does) and opens F2. New / Edit / Archive are hidden in All mode; in branch mode the Super Admin acts as an Accountant would.
- **F8 Above the approval limit.** KDY limit 50,000.00: the rent template's row shows the info tag "Needs approval (above 50,000.00)". Saving from it follows AG-064 exactly. The template itself is never "pre-approved" (R7).

No other code writes `transactions` or balances.

## 6. Business rules
- **R1 A template posts nothing.** No template action touches `transactions`, `ledger_entries`, `accounts.current_balance`, reports, the dashboard, the trial balance, statements or reconciliation marks. An expense exists only after a user saves the S2 form, and it is then exactly what the user submitted (R5). `transactions.expense_template_id` is set only by `POST /expenses` and is never changed afterwards: `PUT /transactions/{id}`, reclassify, void, reverse and approval keep it as it is and never accept it in the body, and void contras and reversal transactions never carry it (review SHOULD 6).
- **R2 Branch-owned.** `branch_id` = the active branch at create, never changed. Every read goes through `BranchScoped`: in branch mode another branch's template returns 404 on every route, and as `template_id` on `POST /expenses` it returns 422 "Template not found in this branch." (the template is read with the scope on, so the message never confirms that it exists elsewhere). A Super Admin in All mode reads every branch's templates (read-only) and cannot create, edit, archive or restore them (422 "Choose a branch first."), nor record an expense in All mode (section 5). Templates themselves are always read with the scope on. `withoutGlobalScopes()` is used only where access is already checked, as CLAUDE.md allows: the name check (R3) and the R7a same-name read filter on the template's `branch_id` explicitly; the template's account is read without the scope after R4 has tied it to the template's branch (as `Transaction::account`); the transaction detail reads its template after the transaction itself passed the branch check; the audit log reads template names for rows already limited to the visible branches.
- **R3 Name.** Trimmed, with inner spaces collapsed, 3-100 characters, unique among the **non-archived** templates of the branch, compared case-insensitively (`LOWER(name)`, portable between SQLite and MySQL). Error "A template named <name> already exists in this branch." Archived templates may share a name; restore re-checks (S1 restore error). The same name in another branch is allowed.
- **R4 Account and category when saving a template.** The account must be in the template's branch, of a money type, with `status = active` ("Choose an active cash, bank or wallet account of this branch."). The category must be of type `expense`, `isEffectivelyActive()`, a sub-category (not a parent, as the entry form), and global or of the template's branch ("Choose an active expense sub-category of this branch."). These are checked at create, at edit and at restore. They are **not** checked again on their own later: a template whose account or category is deactivated afterwards stays as it is and is flagged (S1 tags).
- **R5 Pre-fill (Create from template).** The form takes account, category (parent and sub), amount (empty when null), payee, payment method and description. It **never** takes the date (always today, editable as usual) or the reference (always empty). Files are never copied. An account that is not `active`, or a category that is not effectively active, is **left empty** with "The template's account <name> is inactive. Choose another account." / "The template's category <path> is inactive. Choose another category." Nothing is posted until Save. The server never fills missing request fields from the template: `POST /expenses` validates and posts only what the request contains, with `template_id` as a link. So an inactive account or category is always refused by the existing `LedgerService` checks ("Account is inactive.", "Category must be an active expense category."), even if a stale form sends it.
- **R6 Duplicate guard (Q3).** When `template_id` is sent and the template's `frequency` is not `none`: inside the `incomeOrExpense` transaction, lock the template row (`lockForUpdate`, so two parallel uses are serialised) **as the transaction's first statement**, then look for expenses with the same `expense_template_id` that are `status = posted`, or `status = pending` and not yet past the AG-064 R8 expiry (`requested_on` + 30 days; a request the daily expiry job has not closed yet is already dead, review finding 4), whose **bill date** is in the **same period** as the submitted `txn_date`. The bill date is `requested_date` when it is not null (pending requests, and approved requests, whose `txn_date` is the approval date, AG-064 R6), otherwise `txn_date` (accounting review MUST 1). So October rent requested on 2026-10-28 and approved on 2026-11-02 counts for October, not November. The period is the calendar month, the calendar quarter or the calendar year of that date (Q11), and it is filtered with `whereDate` bounds. Void, reversed, rejected, cancelled and expired rows do not count (a reversed expense was undone, so the bill is still unpaid in the books; review MUST 1). The second of two parallel uses must see the first (AC 19, review finding 1): on MySQL (REPEATABLE READ) a plain read answers from the snapshot taken at the transaction's first plain read, so nothing is read before the template lock and that snapshot is taken after the first use committed; inside an outer transaction, where an earlier read may already have fixed the snapshot, the linked expenses are read with a shared lock (latest committed data). The shared lock is not used otherwise, because its next-key locks make parallel first uses of two different templates deadlock. When one or more are found and `confirm_duplicate` is not true: 409 "This template was already used for <November 2026 | Q4 2026 | 2026>: <ref> (<status>, <date>)[, ...]. Save anyway only if this is a separate bill." Nothing is written and no audit row is created. With `confirm_duplicate: true` the expense proceeds; its audit row carries `duplicate_confirmed: true, duplicate_of: [ref_no, ...]`; when it is held, the approver sees this (R7a). The Audit log gains the filter "Duplicate template use confirmed" (rows of `transaction.expense` and `expense.approval_requested` with `duplicate_confirmed: true`) for the month-end review (review SHOULD 5). The guard only looks at entries linked to this template; an expense recorded without a template is not compared (that would be a general duplicate check, which is not in this item).
- **R7 Approvals unchanged (AG-064).** An expense from a template is an ordinary `POST /expenses`. Above the branch threshold, or by the R2b same-day rule, it is held, with the same requester, approver, R4/R4a segregation, expiry and notifications. A template is never approved, and its amount being "known" or "regular" gives no exemption. Editing a template never changes a pending request or a posted expense. The S1 "Needs approval" tag is information only and uses the branch's current threshold (strictly above it, in cents). The R6 check runs first; the AG-064 R2 and R2b decision then runs unchanged on the submitted amount, so a template neither raises nor lowers the hold (a below-limit split across days stays covered by the AG-064 R16 detective line, as for any expense).
- **R7a The approver sees the template facts** (accounting review MUST 2, replaces the Q7 assumption; sign-off finding 2). For a held expense with `expense_template_id`, the AG-064 "Expenses to approve" row, the approve dialog and the S3 detail show:
  - "From template <name>";
  - "Changed from template: Amount (template 150,000.00), Paid to (template S. Fernando (landlord))" when `template_changes` is not empty, with the template's value at use for each changed field;
  - the template compared with the **last use an approver approved** (`approval_status = approved`), not with its last use, which may have posted below the limit with nobody looking (sign-off finding 2 b): (warning) "Template changed since its last approved use (<ref>, version <a> -> <b>, last changed <date> by <name>): Paid to (was S. Fernando (landlord)), Paid from (was KDY Bank)" when the version is higher than the one that use recorded, listing every compared field whose value differs between the two versions;
  - when no use of the template was ever approved: (warning) "First use of this template: created <date> by <name>; last changed <date> by <name>", or "No earlier use of this template was approved (<n> earlier uses not reviewed): created ..." when it was used below the limit before;
  - (warning) "A template with the same name was archived <date> by <name> (<reason>); this one is a different template" when a template of the same name (case-insensitive) in the branch was archived in the last 90 days (sign-off finding 2 a: archive and re-create gives a new template with no history);
  - (warning) "Second use for <November 2026>, confirmed by the requester: <ref> (<status>, <date>)" when `duplicate_confirmed`.
  All of these come from the use's audit row (R11), so they show what was true at request, not the template as it is now. Nothing else in AG-064 changes. The "changed since its last approved use" line names everyone in `template_authors` (R7b), with the date of the last change (accountant sign-off finding B).
- **R7b The template's author does not decide its use** (accountant sign-off finding A). The default Branch Admin role holds both `expense.edit` and `expense.approve`, so without this one person could set the standing payment data (payee, account, amount) and approve the payment that relies on it, while the Cashier records it in good faith. The use's audit row stores `template_authors` (R11): when `template_first_review` is true, the user ids of every `expense_template.created` and `expense_template.updated` row of the template; otherwise the user ids of the `expense_template.updated` rows whose `version` is above `template_reviewed_version` (an empty list when the template is unchanged since its last approved use). A non-Super-Admin approver whose id is in it gets 403 "You set up or changed this template since its last approved use. Someone else must approve it." on approve and on reject (`ExpenseApprovals::lockedForDecision`, after the R4a check, as R4/R4a); `canApprove` (S3 detail) and the widget's `can_approve` are false for them, and the widget row and card show the tag "Another approver must decide" with no buttons (`template_author: true` on the row). The `ExpenseApprovalRequested` in-app notification and email skip them. A Super Admin may still decide (the owner, as the R4b exemption). Uses posted at once (below the limit) are not affected: nobody approves them, and the month-end review covers them (release note 4).
- **R8 Locks and dates.** Templates have no date, so period locks and fiscal-year closes do not affect creating, editing, archiving or restoring them. The expense saved from a template is checked for its own `txn_date` as today (period open, year open, date <= today). The AG-033 late-entry warning for a reconciled bank account works as today.
- **R9 "This period" and "Last used"** (display only, S1). This period = the template's period that contains `BusinessDate::today()`, with the linked expenses whose bill date (R6: `requested_date` when not null, else `txn_date`) is in it, void/reversed/rejected/cancelled/expired excluded (expired includes a request past `requested_on` + 30 days that the job has not closed yet, R6), and their status labels. `null` when `frequency = none`. Last used = the latest bill date of any linked expense that counts (R6).
- **R10 Archive, never delete.** Archive sets `archived_at`, `archived_by` and `archive_reason`; restore clears them. An archived template is hidden from the picker, cannot be used (422 "This template is archived." on `POST /expenses`) and cannot be edited. Expenses already linked keep their `expense_template_id` and show "(archived)" on S3. There is no delete endpoint and no delete in the UI. Creator or editor deactivated or removed from the branch: the template stays and stays usable; S1 shows "Created by <name>" with the usual "Inactive" tag.
- **R11 Audit** (`AuditLog::record` on the template, branch = the template's branch). `expense_template.created` new = all fields (amount as a decimal string); `expense_template.updated` old/new of the changed fields only, plus `version` old/new (no row and no new version when nothing changed); `expense_template.archived` old `{archived_at: null}` new `{archived_at, reason}`; `expense_template.restored`. On use, the existing `transaction.expense` row (posted at once) or the `expense.approval_requested` row (held) adds `template_id`, `template_name` and `template_changes`: the list of fields among `account_id, category_id, amount, payee_payer, payment_method, description` whose submitted value differs from the template at that moment (amount compared in cents; when the template has no amount, `amount` is never listed); `template_values`: the template's value of each listed field at that moment (amount as a decimal string), so the difference can be shown later even after the template is edited again; `template_labels` (account / category names for the listed id fields); `template_version`; and the R7a comparison (accounting review MUST 2, sign-off finding 2): `template_first_review` (no use of the template was approved yet), `template_unreviewed_uses` (its counted earlier uses, when `template_first_review`), or `template_reviewed_version` and `template_reviewed_ref` (the version and ref recorded by its latest approved use) with `template_changed_since_review` and, when true, `template_review_changes`, `template_review_values` and `template_review_labels` (the compared fields whose value differs between that version and this one, with the old values; the old version is rebuilt from the template's `created` and `updated` rows); `template_authors` and `template_author_names` (R7b, ids and names in the same order); `template_created_on`, `template_created_by`; `template_changed_on`, `template_changed_by` (the latest `expense_template.updated`, when version > 1); and `template_same_name_archived: {id, name, archived_on, archived_by, reason}` (R7a, last 90 days). Add `duplicate_confirmed`, `duplicate_of`, `duplicate_period` and `duplicate_entries` per R6. Refusals (403, 404, 409, 422) write nothing.
- **R12 Money.** `amount_cents` integer; the API accepts and returns decimal strings converted with `App\Support\Money`; the web compares with `toCents`. No floats or bcmath.
- **R13 Edge cases.** A category promoted from branch-only to global (categories R9) stays valid. A branch deactivated: its templates stay; using one fails on the existing branch checks. An account closed (`closed`): treated as inactive (R5 and the S1 tag). A user with `expense.create` in KDY and GAL sees only the active branch's templates. A template's amount above the account's balance: no warning on the template; the block/warn rule applies at save as today. A Cashier changing the pre-filled amount is allowed (bills vary); it shows in `template_changes` and on S3.

## 9. Open questions for the accountant (assumption in bold, work proceeds on it)
- **Q1 Who maintains templates?** **Holders of `expense.edit` (Accountant, Branch Admin, Super Admin) create, edit and archive them; holders of `expense.create` (including the Cashier) use them.** Reason: the payee, amount and account are standing payment data, and the person paying should not be able to change them alone. Alternative: let the Cashier keep their own templates. That is quicker to set up, but a payee or amount change then has no second person looking at it. **Decided (accounting review): agreed.**
- **Q2 Amount optional?** **Yes.** An empty amount means "enter each time" (electricity, water). Rent and salaries carry an amount. The backlog says "stores amount"; an optional amount still meets it for fixed bills. **Decided (accounting review): agreed.**
- **Q3 Duplicate in the same period: block, warn, or nothing?** **A soft block:** 409 with the earlier ref and a deliberate "Save anyway", recorded in the audit (`duplicate_confirmed`). Rent entered twice is the main new risk that templates bring. A plain warning is easy to click past, and a hard block would stop genuine cases (two separate bills, or arrears paid in the same month). **Decided (accounting review): agreed (soft block, audited); the period uses the bill date (MUST 1) and a confirmed duplicate is shown to the approver (MUST 2).**
- **Q4 Automatic or scheduled posting.** **Not built, and not acceptable as a posting** (section 1: no evidence that money left, no human requester for AG-064 segregation, lock and funds failures at night, a repeated wrong amount, false bank lines). Please confirm. If reminders are wanted later, the proposal is a separate backlog item for a reminder only (a "not used yet this period" notification), never a posting or an auto-created pending request. **Decided (accounting review): confirmed, no automatic posting and no auto-created pending request.**
- **Q5 Should a template above the branch limit need approval when it is created or changed?** **No.** The template posts nothing. Every expense saved from it is held under AG-064 by its own amount, so the control runs on each payment. Changes are audited with old and new values. **Decided (accounting review): agreed.**
- **Q6 Reference and attachments on the template.** **Not stored.** A reference or bill number on the template would be copied onto every payment and look like evidence when it is not. The lease agreement belongs with the branch's records, not on each monthly entry. Each payment brings its own receipt (AG-062). **Decided (accounting review): agreed.**
- **Q7 Changes from the template at use.** **Allowed and recorded** (`template_changes` in the audit row and on the transaction detail), with no extra control. Bills vary; the approver sees the actual amount anyway. Should the AG-064 approval widget also show "From template <name>, template amount <x>"? Assumption: **no, not in this item** (it is visible on the detail page). **Decided (accounting review): changes allowed and audited, but the approver must see them: R7a (MUST 2).**
- **Q8 Super Admin in All branches mode.** **Read-only list; Use switches to the template's branch first**, because recording an expense needs a branch (the existing shell hides "Record expense" in All mode). **Decided (accounting review): agreed.**
- **Q9 Shared templates for all branches** (for example a company-wide insurance premium). **No: templates belong to one branch.** Accounts are per branch, so a shared template could not name the account to pay from. **Decided (accounting review): agreed.**
- **Q10 Payment method default for new templates.** **Bank transfer**, since recurring bills are mostly paid by transfer or standing order. The entry form default (Cash) is unchanged when no template is picked. **Decided (accounting review): agreed for bank accounts; the default follows the account type (SHOULD 7).**
- **Q11 Period for the duplicate guard: calendar or fiscal?** **Calendar month, quarter and year.** These match how rent, utilities and annual fees are billed. A yearly template used in a fiscal year that straddles two calendar years is checked against the calendar year of its date. **Decided (accounting review): agreed, calendar periods on the bill date (MUST 1).**

## Accounting review (accountant, 2026-11-20, before development)
Checked against `docs/specs/expense-approvals.md` (AG-064, review and sign-off: R2, R2b, R4/R4a/R4b, R6 posting on the approval date with `requested_date` kept, R16, R21), `docs/specs/bank-reconciliation.md` (AG-033: R5 void of a reconciled line refused, correction by reversal; R8 late entries), CLAUDE.md, `PermissionSeeder::TEMPLATES` (Accountant holds `expense.create` and `expense.edit`; Cashier `expense.create` only) and `LedgerService::reverse` (any posted transaction, expenses included, can become `reversed`). The spec text above has been changed for every finding below.

**Decisions**
- **Q1 Maintenance by `expense.edit`, use by `expense.create`: agreed.** The Accountant holds both keys and can change a template and then use it; that gives no power beyond recording the same expense directly, and the payment control stays where it is (AG-064 hold above the limit, audit below it). What a template adds is that a *different* person relies on standing data; that is covered by MUST 2.
- **Q2 Amount optional: agreed.** A fixed amount is only a suggestion; the saved amount is what the user submits.
- **Q3 Soft block with "Save anyway", audited: agreed.** It is an error-prevention control, not an anti-fraud one (a user can record the same bill without a template), so a hard block or a forced approval would add friction without closing anything. It must not raise false alarms, though (MUST 1), and a confirmed duplicate that is held must reach the approver (MUST 2).
- **Q4 No automatic or scheduled posting: confirmed.** An expense credits a money account and so asserts that money left; only a person who paid can assert that. No auto-created pending requests either (no human requester for AG-064 R4/R4a/R2b). Reminders only, as a separate item.
- **Q5 No approval of the template itself: agreed.** It posts nothing; each expense from it is held by its own amount under AG-064 R2/R2b unchanged. Template edits are audited with old/new values and now versioned (MUST 2).
- **Q6 No reference or attachments on templates: agreed.** A stored bill number or file would be copied as false evidence onto each payment.
- **Q7 Changes at use: allowed and audited, but not hidden from the approver.** The assumption "not shown in the approval widget" is not accepted (MUST 2).
- **Q8 Super Admin All mode read-only, Use switches branch: agreed.** Super Admin expenses stay unheld with the existing `not_required_super_admin` flag.
- **Q9 One branch per template: agreed.** Keeps branch isolation and the account choice valid; no inter-branch effect.
- **Q10 Default payment method Bank transfer: agreed for bank accounts**; for a cash account the default should be Cash (SHOULD 7). Payment method does not affect the ledger.
- **Q11 Calendar periods: agreed**, measured on the bill date (MUST 1).

**Findings**
1. **MUST: the duplicate period uses the bill date, and reversed expenses do not count.** AG-064 R6 posts an approved expense on the approval date, so `txn_date` moves into the next month while `requested_date` keeps the bill date. Comparing posted rows by `txn_date` makes October rent approved on 2 November block November rent (and leaves October looking unused), which trains users to press "Save anyway" and defeats Q3. Use `requested_date` when not null, else `txn_date`, in R6 and R9. An expense corrected by reversal (AG-033 R5/F7) is undone in the books and is excluded like a void. 2. **MUST: the template must not hide changes from the approver.** Two ways a template weakens the AG-064 review: (a) an approver sees a regular-looking "rent" amount and does not know it was changed at use or is a confirmed second use in the same month (R16 only looks at below-limit amounts, so a duplicate above the limit is invisible to it); (b) `template_changes` compares against the template *at that moment*, so an edit to the template just before use (by a user holding `expense.edit`) produces `template_changes = []` and "From template" lends it false authority. Required: templates carry a `version`; the use audit row stores `template_version`, `template_values` and `template_changed_since_last_use`; the AG-064 widget row and approve dialog, the S3 detail and the S2 form show the template name, the changes with the template's values, "Template changed since its last use" and a confirmed duplicate (R7a, R11, S2, S3, S5, API). A template is never pre-approved, and editing it never changes a pending request (AC 28). The split rule is no weaker than for direct entry: same-day splits are held by R2b (AC 27), cross-day splits are AG-064 R16's detective line as today, and a template used twice in a period now raises a 409 and an audit flag, which is more than direct entry gives.
4. **Fine: double entry, balances and period control.** No template action writes `transactions`, `ledger_entries` or `current_balance`; the saved expense goes through `LedgerService::incomeOrExpense` with every existing check (period lock, fiscal year, funds, active account/category); the server never fills fields from the template (R5); amounts in integer cents through `Money`; nothing is hard-deleted (archive/restore, audited); branch isolation through `BranchScoped`, no `withoutGlobalScopes()`. Bank reconciliation is untouched: a template creates no bank line, and the expense saved from it is an ordinary line (R8).
5. **SHOULD: confirmed duplicates are easy to review.** Audit log filter "Duplicate template use confirmed" over `transaction.expense` and `expense.approval_requested` rows with `duplicate_confirmed: true`, for the Accountant's month-end review of below-limit duplicates (which no approver sees).
