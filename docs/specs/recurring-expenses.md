# Spec: Recurring expense templates (create an expense from a saved template, e.g. rent)

## 1. Goal and scope
Backlog **AG-066** (E7 Income & Expense Recording, Could, R3, 3 points): "As a Cashier, I want recurring expense templates (e.g. rent) so that regular payments are faster to enter." AC: template stores account, category, amount, payee; "Create from template" pre-fills the form. Project document: E7 "Record entries with category, sub-category, payee/payer, attachments; edit/void; recurring templates"; supporting table `recurring_templates` ("templates for recurring entries").

**A template is a saved pre-fill for the Record expense form. It posts nothing.** Creating, editing, archiving or restoring a template never writes `transactions`, `ledger_entries` or `accounts.current_balance`. Using a template opens the normal expense form, already filled in. The user checks it and presses Save. That runs the existing `POST /v1/expenses` and `LedgerService::incomeOrExpense` with every existing check: account active and of the branch; category active, of type expense, global or of the branch, parent active; amount > 0; date <= today; period lock and fiscal year open; `assertFunds` in block mode; the AG-064 approval hold (R2 and R2b).

**Decision: no automatic or scheduled creation (Q4).** The backlog asks only for "Create from template". An automatic posting is **not acceptable** in this system, and this spec does not build one, not even as an option:
1. An expense credits a money account, so it records that cash or bank money **has left**. A scheduler cannot know that the rent was actually paid, on which day, from which account or for how much. A posting made without that knowledge is a false entry. The fix would be a void, which adds noise to the audit trail.
2. There would be no human `created_by`. AG-064 needs a requester: R4 says the requester never approves, R4a decides who may approve, and R2b sums the same-day total per user. A system user would either bypass the hold (as Super Admin expenses do) or create requests that nobody owns.
3. A nightly job would hit locked periods, closed years, "Insufficient balance" in block mode and inactive accounts with nobody there to decide. It would fail silently or post into the wrong period.
4. One template edit would repeat a wrong amount or payee every month without anyone looking at it.
5. Bank reconciliation (AG-033) would get book lines that exist only because a schedule ran, not because of a real bank movement.
If the business later wants reminders, the safe form is a **reminder only** (for example a "Not used yet this period" list or an in-app notification), never a posting. That would be a new backlog item. The S1 "This period" column (R9) already shows which templates have not been used yet this period.

What exists (`feature/bank-reconciliation`, 2026-11-20): `TransactionController::storeExpense` with `validated()` (`account_id`, `category_id`, `txn_date`, `amount` decimal 0-2, `payee_payer` max 255, `payment_method` in `cash,bank_transfer,cheque,card,online`, `reference` max 255, `description` max 2000); `EntryFormComponent` (`/transactions/new/:kind`) already reads `?account_id=` (AG-033), keeps the account and date after a save, and has the AG-064 hint (`needsApproval()` from the `amount` signal) and the AG-062 attachment picker; `Category::isEffectivelyActive()`; `Account::MONEY_TYPES` (`cash, bank, wallet`) and `status` (`active`, `inactive`, `closed`); the `BranchScoped` trait; `AuditLogController::GROUPS` and `LABELS`; "Record expense" is hidden in All branches mode (shell).

**Out of scope:** income templates (the story is about expenses; the table has a `type` column so income can follow without a schema change, but only `expense` is accepted); any scheduled, automatic or bulk creation (above); reminders or notifications about due templates (AG-094 is not changed); global or company-wide templates shared by several branches (Q9); stored attachments on a template (each bill brings its own receipt, Q6); placeholders in text such as "{month}"; splitting one template over several categories; a stored reference or bill number (it changes every time, Q6); hard delete of a template; an Excel export of templates.

## 2. Personas and permissions
**No new permission key.** The catalogue in `PermissionSeeder::PERMISSIONS` stays as it is. A new key would also be given to every `*` (Branch Admin) role automatically, and the existing keys already describe the rights:

| Action | Key (in the active branch) | Templates that have it |
|---|---|---|
| See the templates list (S1), the "From template" picker (S2), `GET` endpoints | `expense.create` **or** `expense.edit` | Branch Admin, Accountant, Cashier |
| Use a template (pre-fill and save an expense) | `expense.create` (the save is the normal `POST /expenses`) | Branch Admin, Accountant, Cashier |
| Create, edit, archive, restore a template | `expense.edit` | Branch Admin, Accountant |
| Everything, any branch | Super Admin (`canDo` is always true) | — |

Viewer has none of these keys and sees no Templates menu. A custom role with only `expense.create` may use templates but cannot change them.

**Why the Cashier uses templates but does not maintain them (Q1).** A template is standing payment data: who is paid (payee), how much, and from which account. If the person who pays could also change that data, a payee or amount change would go straight into the next payment with no second person involved. Maintenance therefore needs `expense.edit`, which belongs to the reviewers (Accountant, Branch Admin). Every change is audited with its old and new values (R11). Nobody may grant a key they do not hold; this is enforced by the existing Roles screen, unchanged.

## 3. User flows
- **F1 Accountant sets up rent (KDY Accountant, branch KDY).** Expense templates > "New template" > Name "Rent - Kandy office", Paid from KDY Bank, Category Rent > Office rent, Amount 150,000.00, Paid to "S. Fernando (landlord)", Payment method Bank transfer, Description "Monthly office rent", Repeats Monthly > Save > toast "Template saved." The template appears in the list with This period: "Not used yet (November 2026)".
- **F2 Cashier records this month's rent (KDY Cashier, branch KDY).** Record expense > "From template" picker at the top > "Rent - Kandy office". The form fills in: Date stays at today (2026-11-20), Paid from KDY Bank, Rent > Office rent, 150,000.00, Paid to, Bank transfer, Description. Reference stays empty. Info line: "Filled from template Rent - Kandy office. Check the date, amount and reference against the bill before saving." The Cashier types the reference, attaches the receipt and presses Save. The usual result appears ("Saved as KDY-EXP-2026-000510." or, above the KDY limit, "... sent for approval"). Alternative path: Expense templates > row "Use" opens `/transactions/new/expense?template=<id>` with the same pre-fill.
- **F3 Second use in the same month (duplicate).** On 2026-11-25 someone picks the template again. The form shows (warning) "Already used for November 2026: KDY-EXP-2026-000510 (posted, 2026-11-20)." Save returns 409 and the form shows the message with a "Save anyway" button. Pressing it resends with `confirm_duplicate: true`, the expense is saved, and the audit row records the confirmation (R6).
- **F4 Variable amount (electricity).** The template has no amount. Pre-fill leaves Amount empty and focuses it; everything else is filled in.
- **F5 Account closed later.** KDY Bank is set inactive. The S1 row shows the danger tag "Account inactive". Picking the template fills in everything except Paid from and shows "The template's account KDY Bank is inactive. Choose another account." The user may still save with another active account. An Accountant edits the template to fix it, or archives it.
- **F6 Archive and restore (Accountant).** S1 row menu "Archive" > optional reason > "Template archived." The template disappears from the list and the picker and shows under "Show archived". "Restore" brings it back unless an active template already has the same name.
- **F7 Super Admin, All branches.** Expense templates lists every branch's templates with a Branch column, read-only. "Use" says "Switch to KDY and use". It switches the active branch to the template's branch (as the AG-094 open flow does) and opens F2. New / Edit / Archive are hidden in All mode; in branch mode the Super Admin acts as an Accountant would.
- **F8 Above the approval limit.** KDY limit 50,000.00: the rent template's row shows the info tag "Needs approval (above 50,000.00)". Saving from it follows AG-064 exactly. The template itself is never "pre-approved" (R7).

**Schema** (one migration after `2026_12_01_000000_bank_reconciliation`):
- New table `recurring_templates` (project document name): `id`, `branch_id` (FK, not null, never changed), `type` (string, only `expense` accepted), `name` (string 100), `account_id` (FK accounts), `category_id` (FK categories), `amount_cents` (unsigned bigint **null**, integer cents; `App\Support\Money` converts; no floats), `payee_payer` (255 null), `payment_method` (30 null), `description` (text null), `frequency` (string 10), `created_by`, `updated_by`, `archived_at` (null), `archived_by` (null), `archive_reason` (500 null), timestamps. Index `(branch_id, archived_at)`. The case-insensitive unique name is checked in code (R3), because a plain unique index cannot ignore archived rows.
- `transactions.expense_template_id` unsigned bigint null, FK `recurring_templates`, index `(expense_template_id, txn_date)`.
- Rollback refuses while any `recurring_templates` row exists ("Expense templates exist; rollback would lose them.").

**Code shape (guidance for the developer):** model `App\Models\RecurringTemplate` with `BranchScoped`; service `App\Services\ExpenseTemplates` (validate, store, update, archive, restore, `thisPeriod`, `assertNotDuplicate`); `ExpenseTemplateController`. `TransactionController::validated()` accepts `template_id` and `confirm_duplicate`; `LedgerService::incomeOrExpense` locks the template row and runs the R6 check **inside its existing transaction, before the AG-064 decision**, stores `expense_template_id` on the posted row or on the pending request, and adds the R11 keys to the audit row it already writes. No other code writes `transactions` or balances.

## 6. Business rules
- **R1 A template posts nothing.** No template action touches `transactions`, `ledger_entries`, `accounts.current_balance`, reports, the dashboard, the trial balance, statements or reconciliation marks. An expense exists only after a user saves the S2 form, and it is then exactly what the user submitted (R5).
- **R2 Branch-owned.** `branch_id` = the active branch at create, never changed. Every read goes through `BranchScoped`: in branch mode another branch's template returns 404 on every route, and as `template_id` on `POST /expenses` it returns 422 "Template not found in this branch." (the template is read with the scope on, so the message never confirms that it exists elsewhere). A Super Admin in All mode reads every branch's templates (read-only) and cannot create or edit them (422 "Choose a branch first."). `withoutGlobalScopes()` is not used.
- **R3 Name.** Trimmed, with inner spaces collapsed, 3-100 characters, unique among the **non-archived** templates of the branch, compared case-insensitively (`LOWER(name)`, portable between SQLite and MySQL). Error "A template named <name> already exists in this branch." Archived templates may share a name; restore re-checks (S1 restore error). The same name in another branch is allowed.
- **R4 Account and category when saving a template.** The account must be in the template's branch, of a money type, with `status = active` ("Choose an active cash, bank or wallet account of this branch."). The category must be of type `expense`, `isEffectivelyActive()`, a sub-category (not a parent, as the entry form), and global or of the template's branch ("Choose an active expense sub-category of this branch."). These are checked at create, at edit and at restore. They are **not** checked again on their own later: a template whose account or category is deactivated afterwards stays as it is and is flagged (S1 tags).
- **R5 Pre-fill (Create from template).** The form takes account, category (parent and sub), amount (empty when null), payee, payment method and description. It **never** takes the date (always today, editable as usual) or the reference (always empty). Files are never copied. An account that is not `active`, or a category that is not effectively active, is **left empty** with "The template's account <name> is inactive. Choose another account." / "The template's category <path> is inactive. Choose another category." Nothing is posted until Save. The server never fills missing request fields from the template: `POST /expenses` validates and posts only what the request contains, with `template_id` as a link. So an inactive account or category is always refused by the existing `LedgerService` checks ("Account is inactive.", "Category must be an active expense category."), even if a stale form sends it.
- **R6 Duplicate guard (Q3).** When `template_id` is sent and the template's `frequency` is not `none`: inside the `incomeOrExpense` transaction, lock the template row (`lockForUpdate`, so two parallel uses are serialised), then look for expenses with the same `expense_template_id` that are `status = posted` (by `txn_date`) or `status = pending` (by `requested_date`), whose date is in the **same period** as the submitted `txn_date`. The period is the calendar month, the calendar quarter or the calendar year of that date (Q11), and it is filtered with `whereDate` bounds. Void, rejected, cancelled and expired rows do not count. When one or more are found and `confirm_duplicate` is not true: 409 "This template was already used for <November 2026 | Q4 2026 | 2026>: <ref> (<status>, <date>)[, ...]. Save anyway only if this is a separate bill." Nothing is written and no audit row is created. With `confirm_duplicate: true` the expense proceeds; its audit row carries `duplicate_confirmed: true, duplicate_of: [ref_no, ...]`. The guard only looks at entries linked to this template; an expense recorded without a template is not compared (that would be a general duplicate check, which is not in this item).
- **R7 Approvals unchanged (AG-064).** An expense from a template is an ordinary `POST /expenses`. Above the branch threshold, or by the R2b same-day rule, it is held, with the same requester, approver, R4/R4a segregation, expiry and notifications. A template is never approved, and its amount being "known" or "regular" gives no exemption. Editing a template never changes a pending request or a posted expense. The S1 "Needs approval" tag is information only and uses the branch's current threshold (strictly above it, in cents).
- **R8 Locks and dates.** Templates have no date, so period locks and fiscal-year closes do not affect creating, editing, archiving or restoring them. The expense saved from a template is checked for its own `txn_date` as today (period open, year open, date <= today). The AG-033 late-entry warning for a reconciled bank account works as today.
- **R9 "This period" and "Last used"** (display only, S1). This period = the template's period that contains `BusinessDate::today()`, with the linked expenses dated in it (posted by `txn_date`, pending by `requested_date`, void/rejected/cancelled/expired excluded) and their status labels. `null` when `frequency = none`. Last used = the latest `txn_date`/`requested_date` of any linked non-void expense in any status except rejected, cancelled or expired.
- **R10 Archive, never delete.** Archive sets `archived_at`, `archived_by` and `archive_reason`; restore clears them. An archived template is hidden from the picker, cannot be used (422 "This template is archived." on `POST /expenses`) and cannot be edited. Expenses already linked keep their `expense_template_id` and show "(archived)" on S3. There is no delete endpoint and no delete in the UI. Creator or editor deactivated or removed from the branch: the template stays and stays usable; S1 shows the name with the usual "Inactive" tag.
- **R11 Audit** (`AuditLog::record` on the template, branch = the template's branch). `expense_template.created` new = all fields (amount as a decimal string); `expense_template.updated` old/new of the changed fields only (no row when nothing changed); `expense_template.archived` old `{archived_at: null}` new `{archived_at, reason}`; `expense_template.restored`. On use, the existing `transaction.expense` row (posted at once) or the `expense.approval_requested` row (held) adds `template_id`, `template_name` and `template_changes`: the list of fields among `account_id, category_id, amount, payee_payer, payment_method, description` whose submitted value differs from the template at that moment (amount compared in cents; when the template has no amount, `amount` is never listed). Add `duplicate_confirmed`/`duplicate_of` per R6. Refusals (403, 404, 409, 422) write nothing.
- **R12 Money.** `amount_cents` integer; the API accepts and returns decimal strings converted with `App\Support\Money`; the web compares with `toCents`. No floats or bcmath.
- **R13 Edge cases.** A category promoted from branch-only to global (categories R9) stays valid. A branch deactivated: its templates stay; using one fails on the existing branch checks. An account closed (`closed`): treated as inactive (R5 and the S1 tag). A user with `expense.create` in KDY and GAL sees only the active branch's templates. A template's amount above the account's balance: no warning on the template; the block/warn rule applies at save as today. A Cashier changing the pre-filled amount is allowed (bills vary); it shows in `template_changes` and on S3.

## 7. Worked example
KDY limit 50,000.00. KDY Bank 400,000.00, `expense_negative_balance = block`. Today 2026-11-20.
1. KDY Accountant creates T-RENT (KDY Bank, Rent > Office rent, 150,000.00, monthly) and T-ELEC (KDY Cash, Utilities > Electricity, no amount, monthly). Two `expense_template.created` rows. Balances unchanged.
2. KDY Cashier uses T-RENT and saves with reference "INV-11". It is above 50,000.00, so it is held: `KDY-EXP-2026-000510`, pending, `expense_template_id` = T-RENT, no ledger lines, KDY Bank still 400,000.00. `expense.approval_requested` has `template_id`, `template_changes: []`. S1 This period: "Used: KDY-EXP-2026-000510 (2026-11-20, Pending approval)".
3. 2026-11-25 the Cashier uses T-RENT again: 409 "This template was already used for November 2026: KDY-EXP-2026-000510 (Pending approval, 2026-11-20). ..." Nothing is written.
4. The KDY Branch Admin approves 000510: it posts on that day, Dr Rent > Office rent / Cr KDY Bank 150,000.00, and KDY Bank drops to 250,000.00. The link stays.
5. 2026-12-01 the Cashier uses T-RENT: no duplicate (December), held again as in step 2.
6. T-ELEC used on 2026-11-20 with 12,340.00: posts at once (below the limit), `template_changes = []` because the template has no amount (R11), KDY Cash drops by 12,340.00.

## 8. Acceptance criteria
Data: branches MAIN, KDY, GAL. KDY limit 50,000.00, GAL none. Today 2026-11-20. Users: KDY Accountant (`expense.edit`), KDY Cashier (`expense.create` only), KDY Viewer, KDY Branch Admin, GAL Accountant, Super Admin S1. KDY accounts: KDY Bank, KDY Cash (active), KDY Old Cash (inactive). Categories: Rent > Office rent (global), Utilities > Electricity (global), KDY-only sub Rent > Store room, GAL-only sub Rent > Godown. T-RENT and T-ELEC as section 7.

1. Given the KDY Accountant, When `POST /expense-templates` with T-RENT's fields, Then 201; `amount_cents = 15000000`; `branch_id` = KDY; one `expense_template.created` audit row with branch KDY; no `transactions`, `ledger_entries` or balance change.
2. Given the KDY Cashier, When `POST`, `PUT`, `archive` or `restore` on a template, Then 403 "Missing permission: expense.edit" and no audit row.
3. Given the KDY Cashier, Then `GET /expense-templates` returns 200 with KDY's templates only; given the KDY Viewer, Then 403.
4. Given a non-archived template named "Rent - Kandy office" in KDY, When another is created as " rent -  KANDY office ", Then 422 "A template named ... already exists in this branch."; the same name in GAL is accepted; after the first is archived, the new one is accepted; restoring the archived one then returns 422 "An active template is already named ...".
5. Given account KDY Old Cash, a GAL account, or a parent category (Rent), or an income category, or the GAL-only Rent > Godown, When a KDY template is saved with it, Then 422 with the R4 message. Rent > Store room (KDY-only) is accepted.

## 9. Open questions for the accountant (assumption in bold, work proceeds on it)
- **Q1 Who maintains templates?** **Holders of `expense.edit` (Accountant, Branch Admin, Super Admin) create, edit and archive them; holders of `expense.create` (including the Cashier) use them.** Reason: the payee, amount and account are standing payment data, and the person paying should not be able to change them alone. Alternative: let the Cashier keep their own templates. That is quicker to set up, but a payee or amount change then has no second person looking at it.
- **Q2 Amount optional?** **Yes.** An empty amount means "enter each time" (electricity, water). Rent and salaries carry an amount. The backlog says "stores amount"; an optional amount still meets it for fixed bills.
- **Q3 Duplicate in the same period: block, warn, or nothing?** **A soft block:** 409 with the earlier ref and a deliberate "Save anyway", recorded in the audit (`duplicate_confirmed`). Rent entered twice is the main new risk that templates bring. A plain warning is easy to click past, and a hard block would stop genuine cases (two separate bills, or arrears paid in the same month).
- **Q4 Automatic or scheduled posting.** **Not built, and not acceptable as a posting** (section 1: no evidence that money left, no human requester for AG-064 segregation, lock and funds failures at night, a repeated wrong amount, false bank lines). Please confirm. If reminders are wanted later, the proposal is a separate backlog item for a reminder only (a "not used yet this period" notification), never a posting or an auto-created pending request.
- **Q5 Should a template above the branch limit need approval when it is created or changed?** **No.** The template posts nothing. Every expense saved from it is held under AG-064 by its own amount, so the control runs on each payment. Changes are audited with old and new values.
- **Q6 Reference and attachments on the template.** **Not stored.** A reference or bill number on the template would be copied onto every payment and look like evidence when it is not. The lease agreement belongs with the branch's records, not on each monthly entry. Each payment brings its own receipt (AG-062).
- **Q7 Changes from the template at use.** **Allowed and recorded** (`template_changes` in the audit row and on the transaction detail), with no extra control. Bills vary; the approver sees the actual amount anyway. Should the AG-064 approval widget also show "From template <name>, template amount <x>"? Assumption: **no, not in this item** (it is visible on the detail page).
- **Q8 Super Admin in All branches mode.** **Read-only list; Use switches to the template's branch first**, because recording an expense needs a branch (the existing shell hides "Record expense" in All mode).
- **Q9 Shared templates for all branches** (for example a company-wide insurance premium). **No: templates belong to one branch.** Accounts are per branch, so a shared template could not name the account to pay from.
- **Q10 Payment method default for new templates.** **Bank transfer**, since recurring bills are mostly paid by transfer or standing order. The entry form default (Cash) is unchanged when no template is picked.
- **Q11 Period for the duplicate guard: calendar or fiscal?** **Calendar month, quarter and year.** These match how rent, utilities and annual fees are billed. A yearly template used in a fiscal year that straddles two calendar years is checked against the calendar year of its date.
