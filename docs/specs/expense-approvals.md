# Spec: Expense approvals (expenses above a branch's limit wait for approval before they post)

## 1. Goal and scope
Backlog **AG-064** (E7, Could, R2, 5 points): "As a Branch Admin, I want expenses above a limit to require approval so that spending is controlled." AC: per-branch expense approval threshold; pending expenses don't reduce balance until approved. Project document 7.3 step 3: "If above the branch expense threshold it waits for approval; otherwise it posts immediately and the balance drops"; section 3: "Branch Admin / Manager ... approves branch expenses"; permission catalogue lists `expense.approve`.

**Applies to** expenses a **non-Super-Admin** user records through `POST /v1/expenses` whose amount is **above** the threshold of the expense's branch (R2). **Not** to income, transfers (AG-051 has its own threshold), voids, reclassifications, reversals, year-end lines, nor to any expense a Super Admin records (Q5).

**It reuses AG-051 as built** (`docs/specs/transfer-approvals.md`): the same `transactions` approval columns and states, a pending row with **no `ledger_entries`**, posting through `LedgerService::postApproved` on the **approval date**, the same expiry (30 days on `requested_on`), the requester-never-approves rule, the R9 error order, the R10 races, and the `ledger:verify` V9 check. It adds the AG-094 notification kinds of R11 (`expense.approval_requested`, `expense.approval_decided`) and the approval-request email for expenses.

What exists (`feature/notifications`, 2026-11-20): `transactions` has `approval_status, requested_date, requested_on, approval_threshold, approval_note, decided_by, decided_at, approved_by, approved_at`; `LedgerService::incomeOrExpense` posts at once (checks: category active and of type `expense`, category global or of the account's branch, account active, `assertOpenFor`, `assertFunds` when `expense_negative_balance = block`); `TransferApprovals` (states, labels, `close`, `expire`, `assertPending`); `LedgerChecks::withoutLines` (V1) already skips `pending|rejected`, `approvalRequests` (V9) is type-agnostic; `TransactionSearch::STATUSES` has `pending, rejected`; `ReportService::countedTransactions` counts `posted|reversed` (plus voids with their contras); `PUT /transactions/{id}` and `void` refuse non-posted rows; attachments (AG-062) can be added to any income/expense row not void; `SendInAppNotifications`, `InAppNotifications`, `TransferApprovalRequestedMail`, `users.approval_request_email`; core web `approvals.ts` (`ApprovalDialogComponent`, `approvalLabel`, `toCents`).

**Out of scope:** income approval (Q9); multi-level or amount-band approvers; editing a pending expense (cancel and record again); changing the category at approval (reject with the reason); reserving funds (AG-051 Q1 decision applies); an email to the requester on the outcome (in-app only, Q7); a company-wide expense threshold (per branch only); approval by MAIN of branch expenses (Q1). (A same-day split **hold** rule is **in** scope, R2b, accounting review MUST 3.)

## 2. Personas and permissions
**New key `expense.approve`** in `PermissionSeeder::PERMISSIONS`, right after `expense.void`. Meaning: may approve or reject pending expenses **of the branch the role belongs to** (R3). Unlike `transfer.approve` it counts in every branch, not only MAIN.

| Template | Has it | Note |
|---|---|---|
| Branch Admin (`*`) | yes, automatically (new key propagates to `*` templates) | approves its own branch's expenses (project document section 3) |
| Accountant, Cashier, Viewer | no | a Super Admin or Branch Admin holding the key may add it to a branch's Accountant role (Roles screen; nobody grants a key they do not hold) (Q11) |
| Super Admin | yes (all keys) | any branch, any mode |

Other keys: `expense.create` (record, cancel own request), `transaction.view` (lists, detail, widget), `super` (threshold, R18). The schema migration inserts `expense.approve` where missing, gives it to the `*` templates and to every branch role that already holds **every** other catalogue key (unmodified Branch Admin copies), writing one `role.updated` audit row per role with `source: 'migration expense_approvals (AG-064)'`, exactly as AG-051 did; rollback removes it.

**Segregation:** the requester (`created_by`) can never approve or reject their own request, Super Admin included (R4). A request made by a **branch user manager** (a user holding `user.create`, `user.edit` or `role.manage` through a role in the expense's branch, i.e. the Branch Admin by default) can be approved or rejected **only by a Super Admin** (R4a, accounting review MUST 1): a Branch Admin must not be approved by people they appoint. An approval where the approver brought the requester into the branch is flagged to the Super Admins (R4b, MUST 2). An approver gains no right to record, edit, void or change the threshold.

## 3. User flows
- **F1 Set the limit (Super Admin).** Branches > KDY > Edit > "Expenses above this amount need approval" = 50,000.00 > Save > "Branch saved.". Empty = never (default for every branch); 0 = every expense of that branch. If KDY has no active user with `expense.approve` other than the Super Admin, the save succeeds and shows the R18 warning.
- **F2 Request (KDY Cashier, branch KDY).** Record expense > KDY Cash, Utilities > Electricity, 75,000.00, date 2026-11-18, payee, reference, bill attached. As the amount passes the limit the form shows "Above 50,000.00: this expense needs approval before it is posted. Do not pay until it is approved." and the button reads "Send for approval". Submit > toast "KDY-EXP-2026-000456 sent for approval. Balances do not change until it is approved." The files upload to the pending entry as today. Checks run now (R5); nothing posts.
- **F3 Approve (KDY Branch Admin, X-Branch-Id KDY).** Dashboard > "Expenses to approve" > row KDY-EXP-… 75,000.00, "Available now 200,000.00", Files 1 > Approve > dialog "Posts KDY-EXP-… (75,000.00) from KDY Cash to Utilities > Electricity. Funds and period locks are checked now." + "Posting date: today (2026-11-20). Requested for 2026-11-18." + optional comment > Approve > posted on today's date; KDY Cash drops. The KDY Cashier's bell shows "Your expense request KDY-EXP-… was approved and posted."
- **F4 Reject.** Same row > Reject > reason (required, 10-500) > the row becomes "Rejected"; nothing posts; requester's bell shows "...was rejected by <name>."
- **F5 Cancel (requester).** Dashboard "My expense requests" (or the detail page) > Cancel request > optional reason > "Request cancelled.". No notification.
- **F6 Expiry.** Still pending 30 days after `requested_on`: the nightly job expires it; requester's bell "...expired after 30 days."
- **F7 Branch Admin's own expense.** The KDY Branch Admin records 80,000.00: it waits. Only a Super Admin can approve or reject it (R4a; a second KDY Branch Admin or an Accountant given `expense.approve` cannot); only Super Admins are notified; the KDY Branch Admin sees it under "My expense requests" with "Requested by you", no buttons.
- **F8 Super Admin, All branches.** "Expenses to approve" lists every pending expense of every branch with a Branch column; the Super Admin may approve or reject any request they did not make. A Super Admin's own expenses never wait.
- **F9 GAL with no limit.** GAL's limit is empty: every GAL expense posts at once, whatever KDY's limit is.

## 6. Business rules
- **R1 States** (as AG-051 R1). `approval_status`: `null` "Not required"; `pending` (`status = pending`); `approved` (`status = posted`, may later become `void` through the normal void); `rejected`, `cancelled`, `expired` (all `status = rejected`, final, never posted). Moves only `pending -> approved|rejected|cancelled|expired`. Rows are never deleted.
- **R2 When approval is required** (decided in `LedgerService::incomeOrExpense` at request): type `expense`, user not Super Admin, the **account's branch** threshold not null, and `Money::toCents(amount) > threshold cents`. Threshold 50,000.00 holds 50,000.01 and posts 50,000.00 at once; 0 holds every expense; null never. The threshold at request time decides and is stored in `approval_threshold`; later changes do not touch existing requests.
- **R2b Same-day split hold** (accounting review MUST 3, Q6). Also held, under the same conditions (expense, user not Super Admin, threshold not null): when this amount **plus** the user's own **posted** expenses (`status = posted`, `approval_status` null) in the same branch and the same category (`category_id`) with the same `txn_date` exceed the threshold. Example: limit 50,000.00, the Cashier posted 30,000.00 Utilities > Electricity dated 2026-11-18; a second 30,000.00 dated 2026-11-18 is held; one dated 2026-11-19 posts. `hold_reason` = `same_day_total` (else `threshold`), the form toast adds "Together with your other expenses in this category dated <date> (<amount>) this is above the limit." The same-day sum is read with a locking read inside the request transaction (two parallel halves must not both post). Approved requests are not summed (they were already authorised). **Compensating control:** a Super Admin expense above a non-null threshold posts at once and its `transaction.expense` audit row carries `approval: 'not_required_super_admin'` (the existing Audit log `approval` filter lists it).
- **R3 Who may approve or reject.** A Super Admin (any mode, All branches included), or a user holding `expense.approve` in the expense's branch **while X-Branch-Id is that branch**. Nobody else: the `perm:expense.approve` middleware checks the key in the active branch (403 "Missing permission: expense.approve"), and a row of another branch is not visible in branch mode (404, R9), so a GAL or MAIN Branch Admin can never decide a KDY expense (Q1). The row is read with `withoutGlobalScopes()` only for the visibility check itself (expense's branch = active branch, or Super Admin in All mode).
- **R4 Not the requester.** `created_by` = current user -> 403 "You recorded this expense. Someone else must approve it." (Super Admin included).
- **R4a Requests by a branch user manager: Super Admin only** (accounting review MUST 1). When the requester, **at request time**, holds `user.create`, `user.edit` or `role.manage` through a role in the expense's branch, the request is marked Super Admin only (stored in the `expense.approval_requested` audit row as `super_admin_only: true` and derived the same way at decision time; if either says so, the rule applies). A non-Super-Admin approve or reject -> 403 "This expense was recorded by a user who manages this branch's users. Only a Super Admin can approve it." Cancel by the requester is unchanged. Reason: the Branch Admin appoints the branch's other approvers (Roles screen, Q11) and could otherwise be approved by a subordinate or a second account they created.
- **R4b Approver brought in the requester (detective, Q12, accounting review MUST 2).** At approval, `approver_onboarded_requester` is true when an audit row `user.created`, `user.invited` or `user.role_assigned` for the requester in the expense's branch has `user_id` = the approver and is dated within **90 days** before the request's `requested_on`. Approval stays allowed. When true: the widget row and dialog show it (S3), the `expense.approved` audit row carries `approver_onboarded_requester: true` (Audit log `approval` filter value `approver_onboarded_requester`), and every active Super Admin gets an in-app `expense.approval_flagged` notification (R11).
- **R5 Checks.** At request: everything `incomeOrExpense` checks today (category active, of type expense, global or of the account's branch, parent active; account active and of the active branch; amount > 0; date <= today; period and year open for the requested date; `assertFunds` when `expense_negative_balance = block`). Then the row is created with `status = pending`, `approval_status = pending`, `requested_date = txn_date`, `requested_on = BusinessDate::today()`, `approval_threshold`, all entry fields (account, category, payee, payment method, reference, description), and `ref_no` (same format, year of the requested date, e.g. `KDY-EXP-2026-000456`). **No ledger lines.** At approval: `LedgerService::postApproved` locks the row and the account, repeats every check for the **approval date** against the **current** balance and the **current** category/account/branch state, writes the lines (`PostingRules::incomeExpense`: Dr the category's expense account, Cr the money account) dated the approval date, sets `txn_date` = approval date, `status = posted`, and writes the normal `transaction.expense` audit row. `ref_no` is kept. A failed check returns 422 with the LedgerService message (e.g. "Insufficient balance in KDY Cash (available 40,000.00).", "Category must be an active expense category.", "The period 2026-11 is locked.") and the request **stays pending**.
- **R6 Posting date** = `BusinessDate::today()` at approval (Q2, as AG-051 MUST 1). `requested_date` kept. No `posting_date` input. A request whose requested month was locked meanwhile still posts on the approval date; a December request approved in January posts in the new fiscal year under its old `ref_no`.
- **R7 Reject and cancel.** Reject: approver (R3, R4), comment 10-500 required. Cancel: only `created_by`, comment optional. Both write only approval columns, never ledger or balances.
- **R8 Expiry.** `expenses:expire-approvals`, daily 00:35 Asia/Colombo (`onOneServer`, `withoutOverlapping`): every pending expense with `whereDate(requested_on) <= BusinessDate::today() - 30 days` becomes `expired`, row by row under the R10 lock. `expires_on = requested_on + 30`. Same constant `EXPIRY_DAYS = 30`.
- **R9 Errors on approve/reject/cancel** (in order; nothing written, no audit, no event on any): 404 not found or not visible (not in the active branch and not Super Admin); 422 "This entry is not waiting for approval." (`approval_status` null, or the row is not an expense on the expense routes / not a transfer on the transfer routes); 403 R4 / cancel-by-other; 403 R4a (approve/reject only); 422 "This request was already <approved by X on D | rejected by X on D | cancelled by the requester on D | expired on D>."; 422 field errors; 422 LedgerService messages (approve only).
- **R10 Races.** `DB::transaction` + `lockForUpdate` on the row + conditional update `where approval_status = 'pending'`: of two approvals, approve vs reject/cancel, or any vs the expiry job, exactly one wins; the loser gets the R9 "already …" 422; one set of lines and one `transaction.expense` row. Account rows are locked by LedgerService, so two approvals on the same account cannot both pass on one balance.
- **R11 Notifications (AG-094) — two new kinds**, written by `SendInAppNotifications` (synchronous, database channel, exceptions reported and swallowed, as AG-094 R3), recipients only `active`, never the actor, deduped:

| Event | kind | Recipients | Branch tag | url | Title / body |
|---|---|---|---|---|---|
| `ExpenseApprovalRequested` | `expense.approval_requested` | active users holding `expense.approve` through a role in the **expense's branch**, plus active Super Admins, except the requester; for an R4a request **only** active Super Admins (same for the email) | expense's branch | `/transactions/{id}` | "<ref> needs approval" / "<branch code> <account name>, <category > sub-category>, <amount>, requested by <name>" |
| `ExpenseApprovalDecided` approved / rejected / expired (not cancelled) | `expense.approval_decided` | requester | expense's branch | `/transactions/{id}` | "Your expense request <ref> was approved and posted. You may now pay it." / "...was rejected by <name>. Do not pay it." / "...expired after 30 days. Do not pay it." |
| `ExpenseApprovalDecided` approved with R4b true | `expense.approval_flagged` | active Super Admins, except the approver | expense's branch | `/transactions/{id}` | "<ref> approved by the user who added the requester" / "<branch code> <amount>, requested by <name>, approved by <name>". **Not** marked read by R6 |

  Payee, reference, description and comments are never copied (AG-094 R1: no user-typed text). **R6 stale rows:** on `ExpenseApprovalDecided` (any state, cancelled included) all unread `expense.approval_requested` rows for that `transaction_id` are marked read. **R5 redaction:** an `expense.approval_requested` row is also redacted when the reader is not a Super Admin and no longer holds `expense.approve` in that branch. Constants `InAppNotification::EXPENSE_APPROVAL_REQUESTED`, `EXPENSE_APPROVAL_DECIDED`, `EXPENSE_APPROVAL_FLAGGED`. **AG-094 spec** (`docs/specs/notifications.md`) is updated in the same pull request: section 1 out-of-scope no longer says "notifying about income/expense" (expense approvals are now in), section 2 adds the expense approver persona, R1 adds the three rows above (accounting review MUST 5).
  **Email:** new queued `ExpenseApprovalRequestedMail` (mail only, `afterCommit`) to each approver recipient whose `approval_request_email` is true. Subject "Expense <ref> needs your approval"; body: branch code, account name, category > sub-category, amount, requested by, requested for, expires on, action "Open the expense" -> `<frontend_url>/notifications/<that user's in-app row uuid>`. No balance or "available" figure, no payee, reference, description or file. `shouldSend` re-checks: recipient active, still an approver of that branch (or Super Admin), preference still on, request still pending. The **same** preference `approval_request_email` covers transfers and expenses; S2 of AG-094 relabels the checkbox "Email me when a transfer or expense needs my approval". No email to the requester on the outcome (Q7).
- **R12 Audit** (`AuditLog::record` on the transaction, branch = expense's branch): `expense.approval_requested` new `{ref_no, amount, requested_date, requested_on, account_id, category_id, threshold, hold_reason, same_day_total, super_admin_only, other_pending_from_account, files_count:0, status:'pending'}`; `expense.approved` old `{approval_status:'pending'}` new `{approval_status:'approved', posting_date, requested_date, comment, all_branches, approver_branch, available_before, files_count, paid_before_approval, approver_onboarded_requester, ref_no}`, followed by the existing `transaction.expense` row; `expense.rejected`, `expense.approval_cancelled` (old/new + comment, `all_branches`); `expense.approval_expired` (user null, `expired_on`). Threshold changes: `branch.updated`. Audit log labels: "Expense sent for approval", "Expense approved", "Expense rejected", "Expense request cancelled", "Expense request expired". Refusals write nothing.
- **R13 Readers ignore non-posted requests.** Report and dashboard figures already use counted transactions only; dashboard "Recent" excludes pending/rejected; year-end close and preview ignore them; `PUT /transactions/{id}`, reclassify and void refuse them with their existing messages. **`ledger:verify` V9** already fails on any pending/rejected/cancelled/expired row with a ledger line and on status/approval_status disagreement for any type; extend it to also fail when `approval_status` is not null on a type other than `branch_transfer`, `fund_return`, `expense`.
- **R14 Funds shown, not reserved.** A pending expense never changes `current_balance`. "Other pending from this account" = pending expense requests on the account (`account_id`) + pending transfer requests from it (`from_account_id`), excluding the row itself.
- **R15 Edge cases.** Account, branch or category (or its parent) deactivated while pending: approval fails with the LedgerService message; reject or let it expire. Requester deactivated or removed from the branch: approval still allowed; tag shown in widget and dialog; no notification to an inactive user. Category moved to another branch: approval fails "Category belongs to another branch.". A user in two branches approves only in the branch where they hold the key, with that branch active. Money: integer cents through `Money`; date filters via `whereDate`.
- **R16 Splitting below the limit (detective, in addition to the R2b hold).** Each `to_approve` row carries `below_threshold_7d`: count and amount of **posted** expenses in the same branch and same category, not themselves approved requests, `txn_date` in [today - 6, today], amount <= the branch's current threshold. Information only.
- **R17 Over-commitment warning.** At request, when `amount + other pending from the account (R14) > current_balance`, the request is still created and `warning` = "Other requests on this account already wait for <amount>; together they exceed the balance." Otherwise null.
- **R18 No approver warning.** `PUT /branches/{id}` returns `expense_approval_warning` = "Only the Super Admin can approve <code>'s expenses above the limit." when the threshold is not null and no active non-Super-Admin member of that branch holds `expense.approve` through an active role of that branch; otherwise null. Nothing is refused.
- **R19 Attachments on requests.** Pending: files may be added and removed under the existing AG-062 R2 rights (so the requester can attach the bill after saving); the period-lock rule for removal uses `requested_date`. Rejected/cancelled/expired: add and remove return 422 "This request was not posted; its files cannot be changed." (evidence of the decision is frozen). Approved: normal AG-062 rules. At approval with `files_count = 0` the comment is required (S3, MUST 4).
- **R21 Changes after approval** (SHOULD 9). `PUT /transactions/{id}` (payee, reference, description) and reclassify on an expense with `approval_status = approved` stay allowed under the existing rules (the amount and account cannot change), but their `transaction.updated` / `transaction.reclassified` audit rows carry `after_approval: true` (Audit log `approval` filter) and S5 shows "Changed after approval" with a link to the audit rows.
- **R20 Branch isolation.** All new reads go through `BranchScoped` in branch mode; `withoutGlobalScopes()` only after R3/R9 visibility checks (expense's branch = active branch, or Super Admin in All mode). Branch users never see another branch's pending expenses in the widget, list, report or notifications.

## 9. Open questions (assumption in bold)
- **Q1 (accountant) Who approves?** **The expense's own branch: users holding `expense.approve` there (Branch Admin by default), plus the Super Admin.** Project document section 3 says the Branch Admin approves branch expenses; the story persona is the Branch Admin. MAIN does not approve branch expenses (unlike transfers, the money stays in the branch). Risk: in a small branch the Branch Admin is both approver and user manager (see Q12). **Decided (accounting review): agreed, with R4a: a branch user manager's own requests are approved by a Super Admin only.**
- **Q2 (accountant) Posting date.** **The approval date, fixed, as AG-051 MUST 1.** The expense is recorded in the period it was authorised; `requested_date` is kept. Alternative: the requested (bill) date, which would reopen cut-off for late approvals. **Decided (accounting review): agreed, approval date.**
- **Q3 (accountant) Who sets the limit?** **Super Admin only, per branch on the Branches screen.** A Branch Admin is the approver and could otherwise switch off their own control; AG-092 lists approval thresholds as Super Admin settings. Branch users see the limit read-only. **Decided (accounting review): agreed.**
- **Q4 (accountant) Must a held expense have a receipt attached?** **No, optional**; the approver sees the file count and a "No receipt" tag and may reject. Making it mandatory would block cash expenses with no bill. **Decided (accounting review): optional at request, but approving without a file needs a comment saying why (MUST 4).**
- **Q5 Super Admin expenses?** **Never held** (as AG-051 Q4), flagged in the audit for review.
- **Q6 (accountant) Splitting detective.** **Same branch, same category, last 7 days, posted below the limit** (R16). No hold rule. **Decided (accounting review): the detective line stays, and a same-day hold rule is added (R2b, MUST 3).**
- **Q7 Notify the requester by email of the outcome?** **No, in-app only** (AG-064 does not ask for it; AG-094 covers "know about approvals"). AG-051's decided email is unchanged.
- **Q8 Expiry.** **30 days, as transfers.**
- **Q9 Income above a limit?** **Not held** (out of scope; the story is about spending).
- **Q10 (accountant) Cash paid before approval.** The system cannot stop a cashier paying the bill before approval; a pending expense means "not yet paid". **Assumption: release note / training says not to pay until approved; a rejected request means the money was not paid.** Please confirm whether the help text on S2 should say so ("Do not pay until approved."). **Decided (accounting review): yes, plus the decided notification says whether to pay, and the approver records "already paid" (SHOULD 8).**
- **Q11 Accountant template.** **Does not get `expense.approve` by default**; a branch may add it.
- **Q12 (accountant) Self-approval through a second user.** A Branch Admin can create a user in their branch, request through it and approve. Same residual risk as AG-051 sign-off condition 1; **assumption: accepted, covered by the audit trail (`user.created` + `expense.approved` by the same admin) and the Super Admin's review; no extra control in this item.** **Decided (accounting review): not accepted as audit-trail only. R4a (preventive) and R4b (detective flag + Super Admin notification) are added (MUST 1, MUST 2).**

**Decisions**
- **Q1 Approval in the expense's own branch plus Super Admin, not MAIN: agreed, with R4a.** The money stays in the branch, the project document gives the approval to the Branch Admin, and MAIN has no better knowledge of a branch's bills. But the Branch Admin also appoints the branch's other approvers (Roles screen) and creates its users, so a second branch approver is not independent of them. A request made by a branch user manager (`user.create`, `user.edit` or `role.manage` in that branch) is decided by a Super Admin only. In a branch with one approver this gives: the Cashier's/Accountant's large expenses are approved by the Branch Admin (two people), and the Branch Admin's own are approved by the owner.
- **Q2 Post on the approval date: agreed** (as AG-051 MUST 1). The posting credits a money account, so it records the payment; money must not leave before approval, so the payment belongs to the period in which it was authorised. Back-dating to the bill date would reopen locked or already-reported months. `requested_date` is kept and now also exported (SHOULD 7).
- **Q3 Only Super Admin sets the per-branch limit: agreed.** The Branch Admin is the approver and must not be able to switch the control off or raise it; `branch.updated` carries old/new.
- **Q4 Receipt optional on held expenses: agreed at request, not at approval without a reason.** A held expense is by definition a large one, and the voucher is the audit evidence. Approving with no file needs a 10-500 character comment ("Why is there no receipt?"); `files_count` at approval is in the audit row. This does not block genuine cash expenses with no bill.
- **Q6 Split detection: the 7-day same-category line is kept, but alone it is not enough.** The line is only shown on a row that was held; an expense split into two halves below the limit is never held, so nobody sees the line. Add a preventive same-day rule (R2b): same user, same branch, same category, same `txn_date`, posted total plus this one above the limit -> held. It is one indexed sum in `incomeOrExpense` and has few false positives (a genuine second same-day bill in the same category simply goes for approval).
- **Q10 Cash paid before approval: guidance plus a record.** The system cannot stop it, so: the S2 hint says "Do not pay until it is approved."; the decided notification says "You may now pay it." / "Do not pay it."; the approver can tick "already paid before approval", stored in the audit row, which gives the owner a measure of how often the control is bypassed. Release note: a reject is not a way to account for money already paid; if the bill was genuinely paid, approve it (ticking the box) so the books match the cash; if it should not have been paid, reject it and the cash shortage goes through the normal cash-count/recovery process.
- **Q12 Branch Admin creating a second user to self-approve: not accepted as audit-trail only.** Unlike AG-051 (approval in MAIN, so the trick needs roles in two branches), here it needs only the one Branch Admin role, so it is the easiest route round the control. R4a closes the direct routes (a Branch Admin's own request, or one by a second admin account, goes to the Super Admin). The remaining route, a dummy Cashier account created by the Branch Admin, is flagged (R4b) and the flag reaches the Super Admin in-app, independently of the branch, as AG-094 accounting review 1 required for disputes. Residual risk accepted: a dummy account kept more than 90 days before use; covered by the Audit log and the owner's periodic user review.
