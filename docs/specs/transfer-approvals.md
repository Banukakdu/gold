# Spec: Transfer approvals (large transfers wait for Main's approval before they post)

## 1. Goal and scope
Backlog **AG-051** (E6, Should, R2, 5 points): "As a Super Admin, I want an optional approval step for transfers above a threshold so that large movements are controlled." AC: setting "approval required above amount X (0 = always, blank = never)"; pending transfers do not affect balances; an approver (permission `transfer.approve`) can approve or reject with a comment; the requester is notified of the outcome.

**Applies to** transfers a **non-Super-Admin** user posts through `POST /v1/transfers` whose type is `branch_transfer` or `fund_return` and whose amount is **above** the threshold (R2). **Not** to `internal_transfer` (the money stays in the branch, Q3), `opening_allocation` / `fund_allocation` (Super Admin only, `POST /allocations`), `capital`, `income`, `expense` (AG-064), `reversal`, `year_end_close`, nor to any transfer a Super Admin posts (the Super Admin is the controlling authority, Q4).

**A pending transfer posts nothing.** It is a `transactions` row with `status = 'pending'` and no `ledger_entries`; `accounts.current_balance` and every report figure are unchanged until it is approved. Approval posts it through `LedgerService` (the only writer of ledger lines and balances), with the full checks (funds, period lock, closed year, active accounts) run **again at approval**, dated the **posting date** the approver confirms (default today, R5).

What exists today (`feature/transfer-approvals`, 2026-11-20): `transactions.status` comment reserves `pending|rejected`; `approved_by` (FK users) and `approved_at` exist and are unused (reserved for this item by transfer-receipt.md); `TransactionSearch::STATUSES` = `posted, void, reversed` ("pending / rejected reserved"); `ReportService::countedTransactions` counts only `posted|reversed`; `LedgerChecks::withoutLines` (ledger:verify V1) flags every non-void transaction without lines; AG-052 receipts set `receipt_status` inside `LedgerService::transfer`; `ExportFinished` + `SendExportEmail` is the event + email listener pattern; the scheduler is `routes/console.php`.

**Out of scope:** in-app notifications (AG-094; email now + event hooks, R11), email to approvers (AG-094 "optional email for approval requests"; hook only), expense approval (AG-064), per-branch thresholds (Q2), multi-level approval, editing a pending request (cancel and request again), reserving funds in balances (Q1).

## 2. Personas and permissions
**New key `transfer.approve`** in `PermissionSeeder::PERMISSIONS` (after `transfer.acknowledge`). Meaning: may approve or reject pending transfers. **It only counts in the MAIN branch** (approvals are head office's control over money leaving a branch; R3).

| Template | Has it | Note |
|---|---|---|
| Branch Admin (`*`) | yes, automatically | only the MAIN Branch Admin can use it; a KDY Branch Admin holding it in KDY cannot approve anything (R3) |
| Accountant, Cashier, Viewer | no | Super Admin may add it to MAIN's Accountant role (Roles screen) |
| Super Admin | yes (all keys) | any mode |

Other keys: `transfer.create` (request, cancel own), `transaction.view` (lists, detail), `report.dashboard` (widgets), `report.view` (Transfers report), `super` (setting). The schema migration inserts `transfer.approve` where missing and gives it to `*` templates, as AG-052 did; rollback removes it.

**Segregation:** the requester (`created_by`) can never approve or reject their own request, Super Admin included (R4). An approver gains no right to post or reverse.

## 3. User flows
- **F1 Setting (Super Admin).** First check MAIN has at least one approver besides the Super Admin (Roles screen). Settings > Transfers > "Transfers above this amount need approval" = 100,000.00 > Save > "Settings saved.". Empty = never (default); 0 = every branch transfer and fund return.
- **F2 Request (KDY Accountant).** Transfer money > KDY Cash -> GAL Cash, 150,000.00, date 2026-11-18, note. As the amount passes the threshold the form shows "Above 100,000.00: this transfer needs Main's approval before it is posted." and the button reads "Send for approval". Submit > toast "KDY-TRF-2026-000123 sent for approval. Balances do not change until it is approved." Funds, accounts, lock and date are checked now (R5); nothing posts.
- **F3 Approve (MAIN Branch Admin, X-Branch-Id MAIN).** Dashboard > "Transfers to approve" > row KDY-TRF-… 150,000.00, "Available now 200,000.00" > Approve > dialog: Posting date (default today), Comment (optional) > Approve > posted; KDY Cash and GAL Cash balances change; if the AG-052 setting is on the transfer is now "Awaiting receipt". The requester gets the email "Transfer KDY-TRF-… approved".
- **F4 Reject.** Same row > Reject > Comment (required, 10-500) > Reject > the row becomes "Rejected"; nothing posts; the requester gets the email with the comment.
- **F5 Cancel (requester).** Dashboard "My transfer requests" (or the detail page) > Cancel request > optional reason > "Request cancelled." No email (the requester did it).
- **F6 Expiry.** A request still pending 30 days after it was made is expired by the nightly job (R8); the requester gets the email "expired, request it again if still needed".
- **F7 Super Admin, All branches.** "Transfers to approve" lists every pending request with From/To branches; the Super Admin may approve or reject any request they did not make. A Super Admin's own transfers never wait for approval.

## 6. Business rules
- **R1 States.** `approval_status` (labels): `null` "Not required"; `pending` "Pending approval" (`status = pending`); `approved` "Approved" (`status = posted`, then may become `reversed` as any transfer); `rejected` "Rejected", `cancelled` "Cancelled by requester", `expired` "Expired" (all three `status = rejected`, final, never posted). Moves: `pending -> approved|rejected|cancelled|expired`. Nothing else. A rejected/cancelled/expired row stays forever (nothing is deleted) with no ledger lines.
- **R2 When approval is required** (decided in `LedgerService::transfer`, at request): user is not Super Admin, type in (`branch_transfer`, `fund_return`), threshold not null, and `Money::toCents(amount) > threshold cents`. So threshold 0 holds every such transfer; threshold 100,000.00 holds 100,000.01 but posts 100,000.00 at once. The setting at request time decides; changing it later does not touch existing requests.
- **R3 Who may approve or reject.** Super Admin (any mode), or a user with `transfer.approve` while X-Branch-Id is MAIN. Anyone else, including a branch user with the key in their own branch, gets 403 "Transfers are approved by Main." The row is read with `withoutGlobalScopes()` after this check. A fund return's approver is therefore on the receiving side (MAIN = head office); a branch transfer's approver is neither branch.
- **R4 Not the requester.** `created_by` = current user -> 403 "You requested this transfer. Someone else in Main must approve it." (Super Admin included, for a request they made before becoming Super Admin).
- **R5 Checks.** At request: everything `LedgerService::transfer` checks today (accounts active, different, amount > 0, date <= today, period open and year open for the requested date for every branch with a line, `assertFunds` on the from-account's `current_balance`). Then the row is created with `status = pending`, `approval_status = pending`, `requested_date = txn_date`, `approval_threshold`, `receipt_status = null`, and `ref_no` (same format, year of the requested date). **No ledger lines.** At approval: new `LedgerService::postApproved(Transaction $pending, string $postingDate)` locks the row and the accounts, repeats every check for the **posting date** against the **current** balances, writes the lines dated the posting date, sets `txn_date` = posting date, `status = posted`, `receipt_status` from AG-052 (`TransferReceipts::initialStatus`, so a receipt starts only after approval) and writes the normal `transaction.<type>` creation audit row (`finish`). `ref_no` is kept even when the posting date is in a later year. A failed check returns 422 with the LedgerService message (e.g. "Insufficient balance in KDY Cash (available 140,000.00).", "The period 2026-10 is locked.") and the request **stays pending**.
- **R6 Posting date** (Q5). Default today; allowed `requested_date <= posting date <= today`. When the requested month has been locked or its year closed since the request, the approver must pick an open date (today always works unless today's month is locked).
- **R7 Reject and cancel.** Reject: approver (R3, R4), comment 10-500 required. Cancel: only `created_by`, any branch mode the user can see the row in, comment optional. Both write only the approval columns, never ledger or balances.
- **R8 Expiry.** Command `transfers:expire-approvals`, scheduled daily 00:30 Asia/Colombo (`onOneServer`, `withoutOverlapping`): every `pending` request with `whereDate(created_at) <= BusinessDate::today() - 30 days` becomes `expired`, row by row under the same lock as R10. `expires_on` = request date + 30 days. Constant `TransferApprovals::EXPIRY_DAYS = 30`.
- **R9 Errors on approve/reject/cancel** (in order; nothing written and no audit row on any): 404 not found / not visible; 422 "This entry is not waiting for approval." (`approval_status` null); 403 R3 / R4 / cancel-by-other; 422 "This request was already <approved by X on D | rejected by X on D | cancelled by the requester on D | expired on D>." (not pending); 422 field errors; 422 LedgerService messages (approve only, R5).
- **R10 Races.** Every decision runs in `DB::transaction` with `lockForUpdate` on the transaction row and a conditional update `where approval_status = 'pending'`. Two approvers, approve vs reject, approve vs cancel, or any of these vs the expiry job: exactly one wins; the loser gets the R9 "already …" 422 and nothing is posted twice (one set of ledger lines, one `transaction.<type>` row). Funds: account rows are locked by `LedgerService` as today, so two approvals from the same account cannot both pass on the same balance.
- **R11 Notifications and hooks.** After commit: `App\Events\TransferApprovalRequested` (id) on request, no listener (AG-094 adds approver notification); `App\Events\TransferApprovalDecided` (id, new state, user id or null for expiry) on approve/reject/cancel/expire. Listener `App\Listeners\SendTransferApprovalEmail` sends the queued `TransferApprovalDecidedNotification` to the requester for `approved`, `rejected`, `expired` (not `cancelled`), never to an inactive user. Email: subject "Transfer <ref> approved|rejected|expired"; body: from -> to, amount, requested date, decided by, posting date (approved), comment, link to `/transactions/:id`.
- **R12 Audit** (`AuditLog::record` on the transaction, branch = sending branch): `transfer.approval_requested` new `{ref_no, type, amount, requested_date, from_account_id, to_account_id, threshold, status:'pending'}`; `transfer.approved` old `{approval_status:'pending'}` new `{approval_status:'approved', posting_date, requested_date, comment, all_branches}`, followed by the existing `transaction.<type>` row; `transfer.rejected`, `transfer.approval_cancelled` (old/new + comment); `transfer.approval_expired` (user null, `expired_on`). Setting changes: existing `settings.updated`. Audit log screen labels: "Transfer sent for approval", "Transfer approved", "Transfer rejected", "Transfer request cancelled", "Transfer request expired". Refusals write nothing.
- **R13 Everything that reads transactions must ignore non-posted requests.** Reports and dashboard money figures already use `countedTransactions` (posted/reversed). Also: `LedgerChecks::withoutLines` (ledger:verify V1) and `BackfillPlanner` skip `status in (pending, rejected)`; dashboard "Recent" excludes them; the year-end close and preview ignore them (they have no lines); reversal refuses them (existing "Only posted transactions can be reversed."). Search shows them to both the sending and receiving branch (as other transfers), with their label.
- **R14 Funds shown, not reserved** (Q1). A pending request never changes `current_balance` or "available". The approver sees "Available now" and "Other pending from this account"; the funds check that matters is at approval.
- **R15 Edge cases.** Account or branch deactivated while pending: approval fails with the LedgerService message; reject or let it expire. Requester deactivated: approval still possible, no email. A user who belongs to MAIN and the sending branch may approve requests they did not make. Money: `Money` integer cents only; dates via `whereDate`.

## 9. Open questions (assumption in bold)
- **Q1 (accountant) Should a pending request reserve funds**, i.e. reduce the "available" balance shown and used by other postings? Reserving stops a branch spending money it has asked to move, but creates a second "available" figure and affects expenses posted meanwhile. **Assumption: no reservation; the approver sees "Available now" and "Other pending from this account", and the real funds check is at approval (R5, R14).** Please confirm.
- **Q2 Company-wide or per-branch threshold?** **Company-wide, one setting** (the backlog says "a setting"; AG-064 is per-branch for expenses). A per-branch override can be a later item.
- **Q3 Internal transfers?** **Excluded**: the money stays in the branch (cash to bank). Say if large cash withdrawals from bank should also need approval.
- **Q4 Super Admin transfers?** **Never held**: the Super Admin is the approving authority, and a single-Super-Admin install would deadlock otherwise.
- **Q5 (accountant) Posting date.** **The approver confirms it, default the approval date, allowed from the requested date to today (R6).** Money should not move before approval, so the approval date is normal; the requested date is kept for the audit trail.
- **Q6 Who approves?** **Main (`transfer.approve` in MAIN) or the Super Admin**, never the requester. Not the receiving branch (it benefits from the transfer and already confirms receipt under AG-052) and not the sending branch's own admin.
- **Q7 Expiry period.** **30 days, fixed.** Make it a setting only if asked.

## Accounting review (accountant, 2026-11-20, before development)
Checked against `LedgerService::transfer` (checks at request: active accounts, `assertOpenFor` incl. head office, `assertFunds`), `ReportService::countedTransactions` (posted/reversed only), `TransactionSearch::STATUSES`, `TransactionExporter::statusLabel`, `LedgerChecks`, `BackfillPlanner`, transfer-receipt.md (R8, R14) and `PermissionSeeder`.

**Decisions**
- **Q1: no reservation, confirmed.** Balances are derived from the ledger; a pending request has no lines, so it must not change `current_balance`, "available" or any report. A second "available" figure outside the ledger would be a sub-ledger nobody reconciles, and would block expenses for money that has not moved and may never move (rejected/expired). The control that matters is the funds check against the **current** balance at approval (R5), plus the approver seeing "Available now" and "Other pending from this account" (R14). Finding 3 adds a warning, not a block.
- **Q5: posting date = the approval date (`BusinessDate::today()` at approval), fixed. Not the requested date and not the approver's choice.** The point of the control is that money does not move before approval, so the movement belongs in the period in which it was authorised. Letting the approver back-date to the requested date re-opens cut-off: a request of 31 Oct approved on 3 Nov would change October's branch balances after October's figures were reported but before the lock, and would make AC 10-type lock collisions routine. If the cash in fact moved before approval, that is a control breach; it is recorded when found (approval date) with the requested date kept on the row and in the audit trail, never back-dated. Consequences: R6, S3 dialog and the approve API drop `posting_date` (the dialog shows "Posting date: today (<date>). Requested for <requested_date>."); if today's month is locked for any branch with a line (abnormal), approval returns the LedgerService lock message and the request stays pending.

**Findings**
1. **MUST: R6/S3/API/AC 10-11, posting date fixed to the approval date** (Q5 above). Replace R6 with: "The lines, `txn_date` and the `transaction.<type>` audit row are dated `BusinessDate::today()` at approval; `requested_date` is kept unchanged. The approve request has no `posting_date`; one sent is ignored." AC 10 becomes: "Given a request dated 2026-10-30 and October then locked for KDY, When approved on 2026-11-20, Then 200 and the lines are dated 2026-11-20; Given November locked for KDY (test only), Then 422 'The period 2026-11 is locked.' and the request stays pending." AC 11 becomes: "Given T1 approved on 2026-11-20 with `posting_date = 2026-11-18` in the body, Then lines are dated 2026-11-20." `transfer.approved` keeps `posting_date` and `requested_date` so the gap is visible. A request made in December and approved in January posts in the new fiscal year under its old `ref_no`: agreed (R5), the year-end close ignores it while pending.
2. **MUST: `ledger:verify` must assert, not just skip.** R13 skips `pending|rejected` rows in V1 and the back-fill: agreed, but add a check that every `status in (pending, rejected)` row (and every row with `approval_status in (pending, rejected, cancelled, expired)`) has **zero** ledger lines and `status`/`approval_status` agree (pending<->pending, rejected/cancelled/expired<->rejected, approved<->posted|reversed). Otherwise a bug that posts lines for a rejected request is invisible, because V1 now ignores it. New AC: "Given a rejected request with one ledger line inserted directly, Then `ledger:verify` fails naming the ref."
3. **SHOULD: over-commitment warning at request (Q1).** At request, when `amount + other pending from the from-account > current_balance`, still create the request but return and show "Other requests from this account already wait for <amount>; together they exceed the balance." No block; approval re-checks funds.
4. **SHOULD: splitting below the threshold.** The threshold is per transaction (R2, agreed: strictly "above", 0 = all, empty = never, stored in integer cents, the setting at request time decides). The usual way round it is two transfers of 75,000.00. Add a detective control: the "Transfers to approve" widget (and S7) shows, per request, "Posted below threshold from this account in the last 7 days: N, <amount>"; and R2 also holds a transfer when the same user's **posted** branch transfers/fund returns from the same account on the same business date plus this one exceed the threshold. If the hold rule is deferred, the widget line is the minimum.
5. **Fine: scope.** Super Admin never held is acceptable: the Super Admin is the approving authority and holds `super` anyway; holding them would deadlock a single-Super-Admin install. Allocations (`opening_allocation`, `fund_allocation`) are Super Admin only, so the same reasoning applies. Internal transfers excluded: acceptable for this item (custody stays in the branch and is covered by the bank reconciliation and cash count), but raise a backlog item for large bank-to-cash withdrawals, the classic cash-misappropriation route.
6. **SHOULD: compensating control for Super Admin transfers.** Because they are never held, the `transaction.<type>` audit row of a Super Admin branch transfer/fund return above the threshold carries `approval: 'not_required_super_admin'`, and the Audit log can filter on it, so a second reviewer can see large unapproved movements.
7. **Fine: who approves (R3, Q6).** MAIN `transfer.approve` holders or the Super Admin; for a branch transfer the approver is neither branch, for a fund return the receiving side is head office, which is the intended control. Defaults right: Branch Admin (`*`) only; Accountant only if the Super Admin adds it; never Cashier/Viewer by default. **SHOULD:** S1 refuses nothing but shows a warning on save when MAIN has no active user with `transfer.approve` other than the Super Admin ("Only the Super Admin can approve; requests from MAIN's own admin will wait for you.").
8. **Fine: the requester can never approve or reject (R4)**, Super Admin included, checked on `created_by` after the branch check; cancel is requester only. An approver gains no right to post, reverse or change the threshold (only `super`, logged by `settings.updated` with old/new). A user in both MAIN and the sending branch may approve others' requests (R15): acceptable, two people are still involved.
9. **Fine: re-checks at approval (R5)**: active accounts and branches, open period and year for the approval date in every branch with a line (head office included), funds against current balances under row locks, conditional update on `approval_status = 'pending'` (R10). **SHOULD:** the approve dialog shows "Requester is inactive" when `created_by` is no longer active; approval stays allowed (it is the approver's authorisation) but the approver should know.
10. **Fine: reject and cancel (R7)**: they write only approval columns, never ledger or balances; reject needs a 10-500 reason; rows and their `ref_no` stay forever, so the reference sequence has no gaps an auditor must explain.
11. **SHOULD: expiry (R8) on the business date.** 30 days fixed is fine, and expiry posts nothing. `created_at` is a UTC timestamp, so `whereDate(created_at)` is the UTC date and a request made 00:00-05:29 Colombo is a day "older". Store `requested_at` as the business date (`BusinessDate::today()` at request), compute `expires_on` from it and expire on `requested_at <= today - 30`. AC 17 uses that field.
12. **SHOULD: audit detail (R12).** Complete as to who/when/old/new; refusals write nothing; nothing deleted. Add: `transfer.approved` new values include `available_before` (from-account balance at approval) and `approver_branch` ('MAIN' or 'all'); `transfer.approval_requested` includes `other_pending_from_account`. Because the row is recorded with branch = sending branch, the MAIN Audit log must also list approvals made by MAIN users (filter by user, or record `related_branch_id` = MAIN), so MAIN's reviewer sees its own approvers' decisions.
13. **Fine: reports and figures (R13, S7).** Pending/rejected rows have no lines and are outside `countedTransactions`, so opening + in − out = closing and the sum of branches = consolidated still hold; nothing reaches income/expense. `TransactionExporter::statusLabel` and `TransactionSearch::STATUSES` must gain the new labels (S6 already says so). S7 lists requests pending **now**; label it "Pending approval now (not included above)" so a re-run of an old month is not read as an as-at figure.
14. **Fine: AG-052 receipt.** `receipt_status` stays null while pending and starts at approval, so "in transit" (transfer-receipt R14, `txn_date <= D`) uses the approval date: a request is never in transit before it is posted. `received_on >= txn_date` then correctly refers to the approval date.
15. **SHOULD: period-lock review wording (S8).** With finding 1 a pending request never posts into the month being locked, so the line is information only, never blocking: "N transfer requests (amount) dated in <month> are still pending approval. They are not in <month>'s figures and will post on their approval date." Same count in the Year-end preview.

**Verdict:** approved for development, subject to MUST 1 and MUST 2.
